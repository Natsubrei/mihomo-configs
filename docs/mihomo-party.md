# mihomo-party 使用指南

入口：[`dist/mihomo-party.yaml`](../dist/mihomo-party.yaml?raw=1)。这是 **YAML 覆写**，不是完整订阅或原生内核配置；导入它不需要 Python。

## 首次导入

1. 先导入自己的机场订阅，确认至少有一个节点能正常访问网络。
2. 下载入口文件，在客户端的「覆写」中导入本地 YAML。
3. 将覆写关联到需要的订阅；也可使用客户端的全局覆写功能。
4. 禁用其他负责整体替换 `proxy-groups` / `rules` 的覆写，避免互相覆盖。
5. 应用配置并选择**规则模式**。
6. 在代理页面查看「节点选择」「故障转移」及地区组，确认已出现自己的节点。

默认通过「故障转移」选择节点。AI、登录等对出口变化敏感的业务，可以在对应业务组中手动固定节点。

本入口不修改客户端的 DNS、TUN、IPv6、监听端口、局域网共享和控制接口。没经过 mihomo 的应用流量不会因此自动被代理。

## 远程导入与更新

在 GitHub 打开 [入口文件](../dist/mihomo-party.yaml)，点击 **Raw**，复制浏览器中的完整地址。在客户端创建远程 YAML 覆写并填入该地址，再关联订阅。

- **更新机场订阅**：只要关联仍启用，客户端会重新应用覆写，节点变化不会清除公共策略。
- **更新本项目策略**：在客户端更新远程覆写，再应用配置。
- **使用本地文件**：需要自行下载新版本并重新导入；本地文件不会自动跟随 GitHub 更新。
- 如果以前导入的是另一个仓库的地址，请重新添加本仓库入口；新仓库不会自动接管旧地址。

不要把机场订阅 URL 填到本项目文件中，也不要直接修改客户端生成的最终配置来代替覆写。

## 如何确认已生效？

检查客户端的最终运行配置和日志：

- `proxy-groups` 包含「节点选择」「故障转移」「规则更新」。
- `rule-providers!` 已由客户端转换成普通 `rule-providers`。
- 地区组有真实节点，或明确使用 `REJECT`，而不是 `COMPATIBLE`。
- 规则集加载成功，没有持续的下载或解析错误。

`rule-providers!` 是 Party 的映射替换语法，**mihomo 内核本身不会处理它**。其他 GUI 需要按自身的覆写机制适配。

## 常见问题

**某个地区没有节点？**

地区按节点名称匹配，不验证真实出口。可以在「节点选择」中直接选择节点，或使用「自动选择」。未识别地区的节点不会被主组丢弃。

**多个机场没有合并？**

`include-all` 只读取当前生效配置里的节点和 providers，不会自动合并未启用的其他订阅。先在客户端或 Sub-Store 合并，或将多个 providers 放进同一份生效配置。

**应用后节点报依赖不存在？**

覆写会替换机场原来的策略组和规则。如果节点的 `dialer-proxy` 或 provider 的 `proxy` 依赖旧组，需要自行保留或改写依赖。节点名也不能与策略组或内置代理重名。

**provider 节点健康状态不更新？**

在自己的 provider 配置中启用 `health-check`。组级测速不能替代所有 provider 的健康检查；Party 入口不会修改未知 provider 的设置。

**规则更新失败？**

先确认「规则更新」选择的节点可用，或 GitHub 原站能够直连。更新失败时保留有效缓存，不要无条件清空 `ruleset/`。详见 [分流策略与排障](policy.md)。
